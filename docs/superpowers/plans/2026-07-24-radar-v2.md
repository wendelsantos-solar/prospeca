# Radar Local V2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring the `radar-elevate` V2 prototype (new navigation + 6 net-new capabilities) into the real `leads` monorepo, wired to the existing Supabase/repository backend — not the prototype's mock store.

**Architecture:** The prototype is a mock-only Lovable app; `leads` is a TanStack Start app on Supabase with a repository abstraction and a discovery/CRM split. We keep the real data layer and port V2 as: (1) a small data-layer extension for activity completion, (2) three pure, unit-tested engines (NBA, Today, Notifications) that operate client-side over the already-loaded CRM leads, and (3) UI (top-nav overhaul + 2 new routes + 2 redesigned routes). All new screens read from `useLeadsList({})`, which already returns every funnel lead with its `lead_activities` embedded — no new cross-lead query is required.

**Tech Stack:** TanStack Start/Router, React 19, Zustand, TanStack Query, Tailwind v4, shadcn/ui, dnd-kit, recharts, sonner, Supabase. Test runner: **bun** (`bun test` from `apps/web`).

## Global Constraints

- Stage ids stay **English**: `new | qualified | contacted | won | discarded`. The prototype's PT ids (`novo/qualificado/contatado/ganho/descartado`) must be translated to these on port. Labels come from `STAGE_LABELS` in `src/lib/constants.ts`.
- Activity UI type union stays: `call | message | meeting | followup | proposal | visit | other` (from `src/types`). DB enum is `call/whatsapp/email/meeting/follow_up/proposal/visit/other`; mapping lives in `src/repositories/supabase.ts` (`ACTIVITY_TYPE_TO_UI` / `ACTIVITY_TYPE_TO_DB`).
- URL paths keep the `/app/*` namespace. Do **not** rename existing route files (avoids breaking `/app/kanban`, `/app/painel`). "Pipeline" and "Análises" are **labels only** over the existing `kanban`/`painel` routes. New screens add `/app/hoje` and `/app/agenda`.
- No new DB migration. `lead_activities` already has `scheduled_at`, `completed_at`, `status`, `priority` — sufficient for Today/Agenda/NBA/Notifications.
- All user-facing copy is Portuguese (pt-BR), matching the existing app.
- Both repositories must stay in sync: every new `LeadRepository` method needs a `demo.ts` and a `supabase.ts` implementation.
- `activity.date` currently maps from `scheduled_at`. Treat `date` as the due timestamp (`dueAt` in prototype terms). Add `completedAt` to the UI type.

```ts
async completeActivity(leadId: string, activityId: string, done: boolean): Promise<LeadActivity> {
  const supabase = getSupabase();
  const { data, error } = await supabase
    .from("lead_activities")
    .update({
      status: done ? "completed" : "pending",
      completed_at: done ? new Date().toISOString() : null,
    })
    .eq("id", activityId)
    .eq("lead_id", leadId)
    .select("*")
    .single();
  if (error) throw new Error(error.message);
  return mapActivity(data as ActivityRow);
},
```

- [ ] **Step 4:** Add `updateActivity` to `src/repositories/supabase.ts`:

```ts
async updateActivity(leadId, activityId, input): Promise<LeadActivity> {
  const supabase = getSupabase();
  const patch: Record<string, unknown> = {};
  if (input.title !== undefined) patch.title = input.title;
  if (input.note !== undefined) patch.description = input.note ?? null;
  if (input.date !== undefined) patch.scheduled_at = input.date || null;
  if (input.priority !== undefined) patch.priority = input.priority;
  if (input.type !== undefined) patch.type = ACTIVITY_TYPE_TO_DB[input.type] ?? "other";
  const { data, error } = await supabase
    .from("lead_activities").update(patch)
    .eq("id", activityId).eq("lead_id", leadId).select("*").single();
  if (error) throw new Error(error.message);
  return mapActivity(data as ActivityRow);
},
```
